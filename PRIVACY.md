# Privacy design

Written for someone deciding whether to trust this code with a real clinical document.
It states what the code actually does, not what it intends.

Owns: containment, the guards, the scanner, why the public repo ships invented data.
Does NOT own: the extraction and validation design (`docs/DECISIONS.md`,
`docs/VALIDATION.md`).

---

## The one-sentence model

A scanned laboratory report is protected health information; this pipeline is built so
that **the document, everything derived from it, and every intermediate that carries a
page header never leave the machine and never reach a commit** — enforced by code that
fails, not by a habit that holds.

## What never leaves the machine, and why

| Stage | Where it lands | Leaves? |
|---|---|---|
| The source PDF | `data/raw/` | never — gitignored, and `*.pdf` is banned repo-wide |
| Page images | `data/pages/` | never — every page render carries the patient header |
| OCR intermediates (`.tsv`, `.hocr`) | `data/ocr/` | never — they are the header as text |
| Evidence crops, contact sheets | `data/crops/`, `data/verify/` | never |
| The dataset | `data/labs.json` | never |
| The dashboard | `dist/dashboard.html` | never — it embeds the whole dataset |
| Chat | `127.0.0.1` only, local model server | never |

There is no cloud OCR call, no hosted-model API, no CDN, no web font, no telemetry, and
no analytics anywhere in `src/`. The built page makes **zero network requests**; that is
checked, not asserted (`tools/check_dashboard.py`).

The local server binds `127.0.0.1` explicitly rather than `0.0.0.0`. A dashboard reachable
from the ward network is a disclosure with a nice UI.

## Four independent controls

Each is cheap, and each catches what the others miss. None of them is a rule someone has
to remember.

### 1. `.gitignore`, written before the document arrives

Ignores `data/` and `dist/`, every document and image extension anywhere in the tree, OCR
intermediates, dataset filenames, **and every copy pattern** — `*.bak`, `*.orig`,
`*copy*`, `*backup*`, `*.export`. A backup of patient data is still patient data, and the
copy is what actually gets committed: it has a filename nobody wrote a rule for.

It also ignores `public_denylist.json` and `phi_patterns.txt`. Those files contain the
exact strings they exist to keep out.

### 2. A run-time refusal

`run.py` checks, on every invocation, that `data/` and `dist/` are ignored by the
repository it sits in, and exits before doing any work if they are not. The pipeline
*writes patient data to disk*; the moment it writes into a tracked directory the leak
already exists, and no later check undoes it.

### 3. A pre-commit hook

`python tools/install_hooks.py` writes `.git/hooks/pre-commit`. It blocks a commit when
staged content includes a patient file type or a path under `data/`/`dist/`, or when any
staged diff matches an identifier from `data/phi_patterns.txt` (gitignored, generated by
the pipeline from the demographics it parses — never committed).

Two details in that hook are load-bearing and were bugs first:

- It strips `\r` before matching. The patterns file written on Windows arrives CRLF, which
  leaves a trailing `\r` on every regex and makes each one match nothing. A guard that
  reports success while checking for identifiers that cannot exist is worse than no guard.
- The match loop runs in a command substitution, not a pipeline, so `FAIL=1` reaches the
  parent shell instead of dying in a subshell.

It echoes filenames only, never the matched identifier.

**Verify it by trying to commit a file containing an identifier and watching it fail.**
An unverified guard is decoration. This one has already caught a real leak — an early
`docs/SCHEMA.md` embedded the source filename.

### 4. The scanner: three layers

`tools/scan_phi.py`, run locally, from the hook, and in CI. Exit code 1 means the tree
must not be published.

| Layer | Catches | Why it is not enough on its own |
|---|---|---|
| **Direct identifiers** | name, hospital/UHID number, phone, sample and accession numbers | The easiest layer to strip, which is exactly why passing it gives false comfort |
| **Quasi-identifiers** | the institution, admission dates, clinician names, age | Nothing here names anybody — see below |
| **Value fingerprints** | the real measured numbers | A repo carrying the true series carries the medical record with the name removed |

The scanner never prints the matched text. Echoing the identifier into a CI log publishes
the thing being protected. It reports the layer, the file and the line.

It also scans **git history** (`--with-history`). A clean working tree in a repository
whose history contains the document is not clean: making the repo public exposes every
commit ever pushed.

## Why the quasi-identifier layer is the one that decides it

This is the layer people skip, and it is the reason a "de-identified" repository usually
is not anonymous.

Take four facts that individually name nobody:

| Fact | Population it describes |
|---|---|
| A named tertiary hospital in one city | tens of thousands per year |
| Admitted within one named eight-day window | a few hundred |
| Age stated to the year | a handful |
| Acute-on-chronic liver failure, in ICU, transplant-listed | **often exactly one** |

Nobody had to publish a name. Anyone holding the ward list, the transplant registry, or
their own memory of that admission recovers the identity from the intersection — and the
repository then hands them the full laboratory record attached to it. The same applies to
the treating clinicians: a report signature is a direct identifier for *them*, and a
strong quasi-identifier for the patient.

The value layer closes the same hole from the other side. A rising bilirubin series with a
particular set of admission dates is as identifying to anyone with access to the chart as
the name would have been. Replacing the name and keeping the numbers is not
de-identification; it is a medical record with the cover torn off.

Hence the rule for anything published here: **no institution, no clinician, no calendar
date, no age, and no real measured value** — not one, not "just the normal ones", because
the normal ones sit in the same series as the abnormal ones and index the same admission.

## Why the public repo ships invented data, not de-identified data

De-identification is a claim about a transformation of real data, and the claim is only as
strong as the adversary you imagined. Every published re-identification result is somebody
having imagined a weaker adversary than the one who turned up.

`tools/make_synthetic.py` avoids the argument entirely. There is no transformation of a
real value anywhere in it: the series are written from published reference ranges and
textbook trajectories for a synthetic case of acute-on-chronic liver failure. Nothing in
it derives from an individual, so there is nothing to re-identify — a guarantee that does
not depend on how clever the attacker is.

It is *clinically shaped* rather than random on purpose. A dashboard demonstrated on noise
shows nothing about whether it works: the trend rules, the score bands and the pattern
detector all need a case that moves in a plausible direction. The demo runs its scores
through `src/scores.py` and its patterns through `src/patterns.py` — the real code paths,
not a parallel fake — so the demo exercises the same logic the pipeline uses.

Its dates are deliberately obvious and far from any real admission, and every observation
carries `provenance.synthetic: true`.

## The CI check

`.github/workflows/privacy.yml` runs on every push and pull request, with
`fetch-depth: 0` so history is scanned too.

| Step | Runs when | Blocks |
|---|---|---|
| Structural checks (`tools/ci_privacy_check.py`) | always, including forks | banned file types, `data/`/`dist/` paths, tracked images and PDFs |
| Pattern scan (`tools/scan_phi.py`) | only where the denylist secret is available | identifiers, quasi-identifiers, value fingerprints, in tree and history |
| Tests + synthetic rebuild + no-network check | always | a demo that no longer builds, or a page that learned to phone home |

The denylist cannot live in the repository, so it is held as a repository secret and
written to a temp file for the duration of the step. Forks and first-time contributors get
the structural checks only — which still block every common failure, and the ones a
contributor is actually likely to make.

The gate is on the pull request, not on a reviewer, because "we caught it afterwards" is
not a recovery: a public commit is forked, cached and indexed within minutes, and making
the repository private later retracts none of it.

## If you fork this for your own documents

In this order. Steps 1–4 happen **before** the PDF is anywhere near the tree.

- [ ] Confirm `.gitignore` still ignores `data/` and `dist/`, then prove it:
      `git check-ignore -v data/ dist/` must print a matching rule for both
      (use the trailing slash — without it git will not match a directory pattern
      against a path that does not exist yet).
- [ ] `python tools/install_hooks.py`
- [ ] **Verify the hook fails.** Stage a scratch file containing a fake identifier of the
      shape yours take, commit, and watch it be refused. Delete the scratch file.
- [ ] Write your own denylist outside the tree — direct identifiers, *and* your
      institution, clinician names, the admission date range, the age, *and* the measured
      values. Point `tools/scan_phi.py` at it.
- [ ] Only now copy the document to `data/raw/`.
- [ ] Never write a real value into a commit message, a docstring, a test fixture, or an
      issue. The scanner reads the tree and the history; it cannot read the issue tracker.
- [ ] Before making anything public: `python tools/scan_phi.py . <denylist> --with-history`
      and read the output. If history is dirty, the repository is dirty — a new repository
      is cheaper than a rewrite you have to trust.
- [ ] Keep the demo synthetic. The moment a real value is used to illustrate a doc, the
      repository is a medical record.
